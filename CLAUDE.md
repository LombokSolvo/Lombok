# Solvo (repo: Lombok) — Junction 2026 hackathon project

## Goal
Solvo, tagline "Fixed costs aren't fixed." A mobile-first money coach for S-Pankki customers that doesn't just show where the money went, it **cuts fixed costs**: it reads the e-invoices that already reach the bank, the AI extracts supplier, price, base fee, consumption and contract end date, shows how much they overpay, and simulates switching the contract with the user's approval. The user never has to photograph or upload anything. Challenge: S-Pankki "Personal Economic Trainer" (Junction 2026). Full plan, demo script, risks and schedule: `PLAN.md` (in Finnish, version 2; it is the source of truth for scope). The draft submission has been sent.

Deadline: draft submission Fri 13.11. 23:59, FINAL Sun 15.11. 10:00, live peer review Sun 10:30–13:00. A working demo beats clean code.

## Demo in one line
Three baskets (1 fixed and regular, 2 fixed and irregular, 3 everyday leakage) and one number, "how much can I safely spend this week?". Solvo has already read the e-invoices and identified each contract → open the electricity contract (AI-extracted fields) → compare → overpay ~€240/yr → one-tap approved switch → safe-to-spend goes up. Coach chat answers questions like "how much did I spend on taxis?" from the real S-Pankki data.

## Scope (from PLAN.md)
- Electricity first. Phone and internet only if time remains.
- Switching is simulated. The pitch explains how a real switch would work (new supplier cancels the old contract).
- No insurance comparison (needs insurance-agent registration). Insurance appears only in the spend basket.
- No native app: a web app that works well in a mobile browser.
- No bill photos and no uploads. S-Pankki has no open API in this challenge, so the demo uses synthetic Finvoice e-invoices linked to the dataset's Utilities payments (in production they would come from the bank's real e-invoice stream).
- Every extracted e-invoice field is shown to the user and editable. Pre-test the demo e-invoices.
- The user approves every switch; the AI never acts alone.
- Competition rules: all code written at the event, MIT licence, synthetic or challenge data only, no existing company.

## Stack
- Next.js (App Router, TypeScript), Tailwind, shadcn/ui. Mobile-first layout.
- Gemini API for reading e-invoices (Finvoice → structured fields) and the coach chat. Key in `.env.local`.
- No auth: hardcoded demo customer. No database planned: 1–3 demo customers preprocessed from the S-Pankki data into static JSON under the app. Add Supabase only if asked.
- Synthetic Finvoice e-invoices for the demo customer(s), tied to their Utilities rows.
- Electricity spot price: a free API (porssisahko.net or ENTSO-E). Supplier prices: a hand-maintained table first, Context.dev later (optional bonus). ElevenLabs voice is an optional wow-factor.
- Deployed on Vercel from `main` (Hobby plan, which caps deployments per day). `vercel.json` turns off preview deployments for `claude/*` branches, so only `main` deploys; CI still runs on every PR.

## Data (S-Pankki challenge dataset)
Cloned from https://github.com/hackjunction/Junction-2026-S-pankki into `data/s-pankki/` (gitignored, never commit it).
- `tx_junction_transactions.csv`: ~346 MB via Git LFS (`customer_id`, `bank_account_id`, `tx_date`, `tx_timestamp`, `category`, `tx_amount_eur`, `balance_after_eur`, `transaction_type`, `merchant_id`, `mcc_code`). Downloaded and checksum-verified. 3.63M rows, 5,100 customers, 2024-10-01 to 2026-09-30, 515 merchants, 36 MCC codes (~78% of rows have one). Categories: Groceries, Restaurants, Transportation, Utilities, Entertainment, Health, Salary, Home & Tech, Housing, Lifestyle, Travel, Invest Deposit, Other Income, Salary Sweep, Invest Withdraw. Debits are negative `tx_amount_eur`. If the file ever starts with `version https://git-lfs`, it is only the pointer again.
- `tx_customers_junction.csv`: 5,100 customers (`customer_id`, `customer_postal_code`, `customer_age`)
- `mtg_*.csv`: mortgage application history and outcomes (not needed for the coach)
- CSVs start with a UTF-8 BOM: read with `utf-8-sig`.
- Preprocess 1–3 demo customers into static JSON for the app; don't read the CSV at runtime.
- Key fact the plan builds on: Utilities payments (342,728 rows, 4,922 customers) average ~€2,000/yr per customer (median ~€1,900) and have no `merchant_id` or `mcc_code`, so the bank can't tell what the contract is.
- Demo persona suggestion (not decided): ~35-year-old from Espoo with high bills and lots of restaurant spending.

## Mobile rules (demo device: iPhone, Safari and home-screen app)
- Design at 375–430px. The layout in `layout.tsx` is a 430px column, centred on laptops.
- Pad pages with `env(safe-area-inset-top/bottom)` (utilities `pt-safe`, `pb-safe`, or `calc(1.5rem+env(...))` when other padding applies). Fixed bottom bars need the bottom inset.
- Use `min-h-dvh` / `100dvh`, never `100vh`. Inputs stay at 16px or larger (iOS zooms on focus otherwise; `globals.css` enforces it).
- Tap targets at least 44px, no hover-only interactions, no popups or new windows (the app should work inside a webview).
- Chat: message list scrolls, input stays attached to the visible viewport above the keyboard. Test on a real iPhone; the Simulator is not available (no full Xcode on this Mac).
- Audio (ElevenLabs) must start from a tap on iOS. No haptics on iOS Safari.
- Never import `src/lib/demo.ts` from a client component (it is `server-only`; the build fails if you do). Compute on the server and pass small props.
- Installable (PWA): `src/app/manifest.ts`, icons in `public/icons/` and `src/app/apple-icon.png`. iPhone installs via Share, Add to Home Screen only (no prompt); Android Chrome gets an Install button. The page `/install` (linked from Profile, `src/components/install-guide.tsx`) shows the steps for each phone, picked from the browser, plus the address to open on a phone. `public/sw.js` (registered by `PwaRegister` in production only) does one thing: when a page can't load offline it shows `/offline`. It never stores pages or data, because Solvo shows today's date and live numbers; keep it that way. `next.config.ts` serves `/sw.js` with no-store so phones don't keep an old one. The embedded preview browser can't register service workers; test with `next start` in real Chrome. Icon: white S from the logo on the slab green (#0c3524).

## Onboarding (first run), calendar and investing rules
- `/onboarding` runs once for a new user (`OnboardingGate` on Home redirects; "Skip for now" is remembered). Four steps: 1 your profile (accept it, or fix it with the small pencils: situation, income and payday, fixed bills), 2 savings goals, 3 investing, 4 your plan. Output: weekly spending budget, monthly transfer to a savings account, monthly room for investing, and what Solvo would move on payday (bills kept safe, irregular pot, savings, investing, spending account). The approved plan lives in localStorage (`src/lib/onboarding-store.ts`, cleared by Reset demo) and replaces the default EUR 200/month savings goal in Home's weekly numbers; the person's income and bill corrections flow through as `monthlyAdjust`.
- `src/lib/profile.ts` guesses student, studying and working, worker, part-time, between jobs or retired from the salary pattern and Kela's study grant (bank code "Opintotuki"; only real Nordea data has it, synthetic customers all come out as workers). `src/lib/schedule.ts` guesses payday and the usual day of rent and utility bills, and builds calendar events. `src/lib/plan.ts` is the allocation maths (rules of thumb at the top, every number traceable). All three are pure; the server pages send only the profile, usual dates and monthly numbers to the browser, never transactions.
- The calendar is part of the app at all times, not part of onboarding: Home has a "Coming up" card (next three weeks of money in and out, `src/components/upcoming-card.tsx`) and a Calendar button on the safe-to-spend card, both always shown. `/calendar` (reached from those): month grid with a "+" marker on days money arrives and a "-" marker on days it leaves. Tapping a day opens it in a sheet: what is expected (money in and out), for a day that has passed also what actually happened (loaded for that one day from `/api/day`, so the phone never holds the whole history), and "Add to this day" for the person's own expected income or costs (optionally monthly), stored in localStorage (`src/lib/calendar-store.ts`). There is deliberately no separate "add" button on the page. It uses the dates the person confirmed in onboarding when there are any. **Salary, the study grant and a side income arrive on the banking day before when the day falls on a weekend or a Finnish bank holiday** (`previousBankingDay()` in `schedule.ts`; Sunday 15 Nov shows as Friday 13 Nov); bills and the person's own dates stay on the day they name; a payday early in the month can land in the month before.
- Bills have specific names, never a bare "Utility bill" where we know better. For the demo customer the names come from the e-invoices (`src/lib/bill-names.ts`: Electricity bill, Grid fee, Phone and internet, with the company shown beside it). For real bank data with merchant names, `billType()` in `src/lib/schedule.ts` names them from the company (Electricity bill, Grid fee, Phone and internet, Insurance, Water bill) and a recurring insurer becomes an Insurance bill. Pages build the schedule with `scheduleFor()` from `src/lib/schedule-server.ts`, not `inferSchedule()` directly.
- Phone testing: `npm run dev` works from a phone on the same Wi-Fi at `http://<your-mac-ip>:3000` (`next.config.ts` allows the machine's own network addresses in dev). Without that, Next's dev server serves the page but blocks its JavaScript, so nothing responds to taps. `npm run dev:live` stays on 127.0.0.1 on purpose and must never be opened from a phone.
- **The demo shows the real date, always.** The synthetic bank data ends on 2026-09-30 and all demo numbers, bills and reminders are built around that day as "today". `src/lib/demo-clock.ts` makes the app display the real date instead: it shifts every demo date by (real today minus 2026-09-30) days as it is formatted (`Intl.DateTimeFormat`), so 30 Sept shows as today and "due in 5 days" stays "due in 5 days". Data, sums and logic are untouched, and screens added later follow automatically if they format dates with `Intl.DateTimeFormat`. Rules: (1) every `page.tsx` must be `async` and start with `await connection()` (from `next/server`), because the clock reads the current time and Next must render per request, never freeze the date at deploy time; (2) code that shows REAL calendar dates (calendar, Coming up) must use `plainFormat()` from `demo-clock.ts`, never a bare `Intl.DateTimeFormat`, or its dates are shifted; (3) real dates need `toDemo()` before looking anything up in the demo data (see `/api/day` use in the calendar) and demo dates handed to the chat model go through `toShown()`; (4) Home's safe-to-spend week is the data's own week (Monday before asOf to Sunday), shown on the real dates the clock gives those days, so its chart (`src/components/week-chart.tsx`: a bar per day spent, dashed bars for what is still free per day, a dashed even-pace line, tap a day for its amount) can start on any real weekday and labels each day by its real date; (5) real Nordea data stays on the same timeline: `src/lib/combine.ts` moves its transactions back by (real today minus 2026-09-30) days so they merge with the demo data, and the clock shifts them forward again when shown, so each appears on its true day (the clock is always on). Don't print raw demo dates (`c.asOf`) as text; format them.
- **Other banks (multi-bank view), opt-in and simulated.** Profile has "Other banks" with "Add another bank" (also an optional row in onboarding step 1). Nothing is assumed: a customer sees no other bank until they add one. Connecting Nordea shows a PSD2-style consent sheet and then attaches DEMO data from `src/lib/second-bank.ts` (a seeded generator: Nordea everyday and savings accounts, a side income S-Pankki can't see, insurance, gym, Netflix, Spotify, transfers between her own accounts and to an investment account). Nothing in it is real. The choice lives in cookies (`solvo_banks`, `solvo_view`, `src/lib/banks.ts`) because pages render on the server; Reset demo clears them. `src/lib/combine.ts` merges the banks into one customer and recomputes baskets and income; Home, plan, calendar, onboarding and the coach all read it through `getEffective()` / `getDemoEffective()` (`src/lib/source-banks.ts`). Home's "All your banks" card (toggle: All banks / S-Pankki only) shows cash and savings, investments, side income, subscriptions, insurance and money moved between her own accounts. Rules: transfers between a person's own accounts and deposits to an investment account are saving, never spending; the coach prompt is built per request and gets a note on connected banks; real bank data is never sent to a model (`getDemoEffective` is synthetic-only).
- **Live banks (the owner's real accounts at Nordea, Revolut, bunq, N26, Wise, Klarna, PayPal and Trade Republic, connected inside the app, local only).** `npm run dev:live` (= `SOLVO_LIVE=1 next dev -H 127.0.0.1 --experimental-https`) adds each bank that is not yet connected as an entry in the Add a bank picker (its own first section, "Your own accounts", each row with what it is: Bank, Neobank, Money app or Trading platform; the same names are left out of the simulated Finland list so none appears twice) and, once connected, as rows in Profile's one "Connected banks" list next to S-Pankki and any simulated bank (per row: what it is, accounts, last sync, connect again, disconnect and delete; one Sync now for all; `LiveBankRows` in `live-banks.tsx`). The person taps a bank, approves with that bank's own login and is back in Solvo; they never open Enable Banking's website. Flow, the same for every bank (`src/lib/live-bank-ids.ts` lists them with the exact names Enable Banking uses): `POST /api/live/start {bank}` (random state token in an httpOnly cookie as `<bank>.<state>`, asks Enable Banking for the bank's approval URL) -> the bank -> `GET /callback` (state checked, single-use code swapped for a session, saved) -> `/connect/live?bank=` (downloads transactions with a progress state, via `POST /api/live/sync {bank}`) -> Home merges the bank in. `POST /api/live/disconnect {bank}` ends the consent at Enable Banking and deletes that bank's files. Files: Nordea keeps `data/private/nordea-api/` and `nordea-customer.json`; the others use `data/private/live/<bank>/`. Code: `src/lib/enable-banking-core.ts` (JWT, calls; shared with `scripts/nordea-psd2.mjs`), `src/lib/live-banks.ts` (guards, session, history, sync, disconnect), `src/lib/nordea-customer.ts` (transaction mapping, shared with `scripts/build-nordea-customer.mjs`), `src/lib/combine.ts` (merging), `src/lib/loopback.ts`. **What open banking gives:** PSD2 covers payment accounts, so these banks return balances and payments, NOT share holdings or portfolio value. Trade Republic is a trading platform: only its cash account comes through, and its consent text says so (the person calls it a trading platform, not a bank, so the app never calls it one). **Euro only:** neobank accounts can hold other currencies, and adding dollars to euros would make every sum wrong, so non-euro transactions and balances are left out (`buildNordeaCustomer`, `pickBalance`); Wise, Revolut and PayPal will therefore look smaller than they are if they hold much in other currencies. **Which banks:** the list is the neobanks, money apps and trading platform in Enable Banking's Finland list (checked 14 Nov 2026: 30 banks); nothing else on that list is an investing platform. Nordnet, Lightyear, Degiro and Scalable are not on it, Nordnet's own API is closed to new customers, and Trading 212 and eToro only offer a key the person creates by hand, so none of them is offered (the earlier simulated Nordnet connector, simulated platforms and `LiveNordnetCard` were removed). Banks cap how far back an app may read, so the sync asks for 535 days and steps down (365, 180, 90, 30) when a bank refuses the start date. **Merging several real banks:** `getSource()` returns the synthetic base plus `real: RealBank[]`; `getEffective()` merges via `combinedCustomer(base, banks, real)`; each bank's accounts get their own ids and carry the bank's name, and the All your banks card shows cash per bank. Money moved between the person's own banks appears twice (out of one, into another), so `matchOwnTransfers` pairs each outgoing payment with an incoming one of the same amount in another bank within three days and marks both "Transfer" (a deposit to an investing platform stays saving at the sending end), or the move would count as spending and the spending at the far end would count again. The mapping recognises investing platforms and broker wording (`INVESTING` in `nordea-customer.ts`: Nordnet, Trade Republic, Scalable, Lightyear, Degiro, eToro and similar names, "savings plan", "Sparplan", ISIN, so a payment to such a platform counts as saving) and pay by wording (`PAY`); both are best effort, written without seeing a real feed from any of the neobanks, so check the first real sync (the builder prints unmapped merchants). **The consent screens say** (plain words, one set for all banks, `liveConsentPoints` in `live-bank-ids.ts`): Solvo can see balances and payments and never move money; you sign in at the bank and Enable Banking, which connects Solvo to the bank, asks you to continue first (that approval screen of Enable Banking always appears, so never claim the person does not see Enable Banking); a short note per bank; access lasts up to 6 months; the data stays on this computer. Rules, each one preventing a leak of real banking data: (1) every route refuses unless `SOLVO_LIVE=1`, not on Vercel, `Host` is localhost/127.0.0.1/[::1], and POSTs carry a same-origin `Origin`; the routes answer 404 when off, so the public app shows nothing; `/api/day` also refuses non-loopback hosts when it serves real data; the bank id from the browser is checked against the fixed list before it touches a file path; (2) the app must be opened at the registered redirect host (`https://localhost:3000`, env `ENABLE_REDIRECT_URL`), or the state cookie does not come along and `/start` says so; (3) real data MERGES with the demo customer like any other connected bank, but it is never sent to a model (`getDemoEffective` stays synthetic-only) and never printed in logs or error messages (counts and dates only); (4) `ENABLE_APP_ID`, `ENABLE_KEY_PATH` (key kept outside the repo), the sessions and all downloaded files stay in `.env.local` and gitignored `data/private/`; (5) the consent is account-information only, as long as open banking allows (180 days, or the bank's own limit from `maximum_consent_validity`, falling back to 90 then 30 if refused; `LIVE_CONSENT_DAYS` lowers it), and there is no payment call anywhere. Connecting again replaces the old consent (the new approval ends it). The app syncs each connected bank itself once a day while `npm run dev:live` runs (`src/instrumentation.ts` -> `src/lib/live-banks-auto.ts`: first check 20 s after start, then hourly, syncs a bank when its last sync is over 24 h old and its consent is valid; one unattended read a day is well inside open banking's limit). It cannot run while the computer is off or the app is stopped, and a hosted copy must not hold real data. Enable Banking's production application is in restricted mode, which lets the owner connect their own accounts at any bank it lists, including all of these. The first `npm run dev:live` asks to install a local certificate (mkcert, may ask for the Mac password); the application's redirect URL must be exactly `https://localhost:3000/callback` in Enable Banking's control panel. Tested end to end against a mock Enable Banking server only (several banks, a bank that refuses old dates, transfers between the banks): a real approval needs the owner's own login at each bank, and what the neobanks actually return (wording, whether share purchases appear, PSU header requirements) is unverified. After the event: Disconnect each bank in the app, delete the app in Enable Banking's control panel, delete the .pem and `data/private/`.

The list comes from `GET /aspsps`, the person approves at the (test) bank, `/callback` swaps the code for a session, and the session lives only in the visitor's own AES-GCM sealed httpOnly cookie (`src/lib/sealed.ts`, key derived from the sandbox key); Home's `LinkedBankCard` reads balances and a year of transactions per request (5 min in-memory cache) and shows cash, last 30 days, recurring payments and the latest payments in its own card, NOT merged into the S-Pankki budget (a test bank's dates and amounts say nothing about Aino's month). Safety: before any call it asks `/application` and refuses anything but `SANDBOX`, so a production key in that slot stops (smoke and a test pin this); only banks Enable Banking lists are accepted; `/api/banks/start` needs a same-origin POST and is capped at 30 a minute; `/callback` is shared with real Nordea and tells them apart by which state cookie matches. Routes are 404 until configured. (2) **Simulated**: when the sandbox is not configured, the picker lists Finland's banks (`FALLBACK_BANKS`) and connecting attaches the synthetic second bank (`src/lib/second-bank.ts`) under the chosen bank's name (cookie `solvo_bankname`, sanitised). (3) **Real accounts, local only** (see Live banks below). There is no investing-platform section: none has an Enable Banking connection except Trade Republic's cash account, which is in the real section. **Try it locally:** `npm run dev:mock-bank` (`scripts/dev-mock-bank.mjs`) runs the app on `http://localhost:3100` against a made-up Enable Banking API (banks in eight countries, an Approve and Cancel bank page, invented accounts), with real Nordea off and nothing real involved. Next allows one dev server per folder, so stop any other `npm run dev` / `dev:live` in this folder first.
- **Profile cards: "What kind of spender are you?" and "Saving for a home" (on Profile, under the header).** The brief asks "What kind of spender am I?". `src/lib/spender.ts` (pure, tested in `scripts/spender.test.mjs`) reads the last 12 months of everyday spending (groceries, restaurants, transport, entertainment, lifestyle) and names the pattern: weekend, evening or balanced, by how far the weekend share of leisure spending and the share after 17:00 sit above the S-Pankki sample's averages (about 40% and 38%). It also gives the weekday spread, the busiest day and the typical purchase. Time of day exists only in the bank's own data: a connected bank that gives dates alone gets no evening figure. It describes, it never advises. Under it Profile reuses the existing "How you compare" block (`CompareSummary` with `ids`/`title`) for restaurants, groceries and transport against the person's age group; real bank data has no age, so it is skipped there like on Home. "Saving for a home" (`src/components/home-equity-card.tsx`) takes a home price and a monthly saving (default: the onboarding plan's saving, else the default goal) and shows the equity S-Pankki's own 200 mortgage applications had (150 approved, median equity 14.7% of the price; rejected 12.5%) and why the 50 were rejected (34 collateral, 8 income, 6 equity, 2 existing debt). The numbers come from `src/data/mortgage-stats.json`, built by `scripts/build-mortgage-stats.mjs` from the dataset: totals and medians only. Rules: it is the synthetic challenge dataset and says so; it is not a loan decision or advice; do not build an approval predictor (in this data salary against the required income did not separate approved from rejected: about 20% of both groups had salary above it); no age limits or ASP figures (see the property goal rule).
- **Subscriptions are their own bracket** (category "Subscriptions", basket 1, fixed and regular): Netflix, Spotify, a gym. Insurance is basket 1 too. Real bank data gets them from merchant names (`scripts/build-nordea-customer.mjs`); the calendar lists any named payee charged the same amount about monthly. S-Pankki's synthetic data has no merchant names, so it shows none until a bank that names merchants is connected.
- **Solvo's call (dentist bill, Aino only)** is a one-way recorded message (`/call`). `CALL_SCRIPT` in `src/data/reminders.ts` names no weekday, date or safe-to-spend number (the demo clock and switches would contradict them); the recording is a static file, `public/audio/solvo-call-en.mp3`, made from that script with ElevenLabs (voice Emily, eleven_v4; make it again if the script changes), so playing it costs no credits and needs no key; if it can't play, the phone's own voice reads the script. Home shows the bill as a card under the safe-to-spend slab with the reminder timeline and a "Play the demo call" button; the call's after screen repeats the timeline. A two-way agent version was built and dropped because live minutes cost too many credits (commits f632cfe and 91b7e51, from PR #64 before its force-push; the agent "Solvo bill coach call (Junction demo)" still exists in the ElevenLabs workspace).
- One look for money moving, everywhere: use `MoneyBadge` and `SignedAmount` from `src/components/solvo/money-badge.tsx` (money out = warm circle with a minus, money in = green circle with a plus; the sign carries the meaning, not only the colour). Other shared bits: `Sheet` (bottom sheet for small edits), `NumberField` and `Stepper` (`fields.tsx`; NumberField keeps raw text so a field can be emptied and retyped, never use a controlled type=number input), the pencil `EditButton` pattern in the onboarding client. All tap targets 44px.
- Investing: Solvo never recommends a product. It sizes a budget ("room to invest": half of what is left after bills, buffer and goals, zero before a starter buffer or while between jobs) and `src/lib/fund-match.ts` screens a catalogue by the person's stated safety, horizon and "environmentally friendly" wish, showing only standard facts (1-7 risk class, EU SFDR label, fee). The person can save funds as interesting and "Start saving" opens the fund's page; nothing is bought. No ranking, no "best", no wording like "we recommend". Keep disclaimers short.
- Property goal: the goal is "Home or property" (a home, a cabin, anything bought with a down payment), not ASP specifically. ASP is only a pointer for first-home buyers: its rules changed in June 2026 and sources disagree on eligibility, so the app states no age limits, saving periods or percentages. Do not add any without a checked source.
